# Atlas11 MVP Completion — Technical Design

## Overview

Atlas11 will be completed as a local, offline-capable coordination-review application. The implementation preserves the existing Python package boundary (`agent/`) and its SQLite/gap foundations, adds the missing typed review lifecycle and deterministic cached scenario, then creates the React dashboard as a strict TypeScript consumer of that API. The primary release path is the canonical seeded scenario (`scenario_key=demo-city-transit-01`, `proposal_id=demo-proposal-01`), which must work without AWS, Bedrock, Chroma, or a locally cached embedding model. Live retrieval and Nova review use the same contracts but are a graceful secondary path. The system will treat review recommendations and redirects only as coordination advice and UI focus; no component will allocate funds, modify commitments, or claim that a district received funding.

The locked stack is Python 3.11+ with FastAPI/Uvicorn, Pydantic v2, SQLite, ChromaDB, Strands Agents and Amazon Bedrock (Nova Pro plus Titan Text Embeddings V2); React 18, Vite, strict TypeScript, Tailwind CSS, Leaflet/react-leaflet, and OpenStreetMap tiles; pytest/Hypothesis/Ruff and Vitest/fast-check. No state-management or frontend framework will be added. `frontend/package.json` will pin exact compatible versions: `react` and `react-dom` `18.3.1`, `vite` `5.4.14`, `typescript` `5.7.3`, `tailwindcss` `3.4.17`, `leaflet` `1.9.4`, `react-leaflet` `4.2.1`, `vitest` `2.1.9`, and `fast-check` `3.23.2`, with matching exact type/plugin dependencies. Existing Python dependency pins in `requirements.txt` will be extended only with exact pins required for FastAPI/Uvicorn/Strands if they are absent.

## Current Baseline and Design Choice

`agent/schemas.py`, `agent/store.py`, `agent/gaps.py`, `scripts/build_need_scores.py`, `scripts/build_index.py`, and the embedding/retrieval boundary provide a usable base. `agent/app.py` currently exposes only `GET /gaps`; the clash-agent lifecycle, cache, live orchestration, evaluation, API/SSE tests, and frontend are unfinished. `agent/store.py` already owns atomic persisted transitions and audit redaction, so FastAPI will orchestrate it rather than duplicating lifecycle logic. `agent/gaps.py` remains the sole read-only gap-data boundary.

There is a conflict in the current `Memo` validator: it permits `redirect_district_id` only with `REDIRECT`, while the authoritative canonical demo requires a `CO_FINANCE` report with a valid redirect district. The design chooses the authoritative demo behavior: `redirect_district_id` means an optional *coordination-focus district*, not a funding action, and is permitted for `CO_FINANCE` and `REDIRECT` (and rejected for `MERGE`/`PROCEED`). The field name is retained to avoid a parallel contract, its docstring and UI copy will make the non-financial meaning explicit, and tests will prove that it leaves all gap values unchanged.

## Shared Contracts and Persistence

`agent/schemas.py` will remain the source of truth for all backend payloads. It will add API response envelopes where needed rather than returning untyped dictionaries: a `ReviewEventReference`/done payload containing `review_id`; typed error detail payloads where FastAPI response models are practical; an `AuditQuery` response is represented as `list[AuditEvent]`; and cache metadata/input contracts internal to the service. `SseEvent.payload` remains JSON-safe but event constructors will validate its required shape by event type before serialization: `status` requires a non-blank progress message, `tool_call` requires `name` and non-negative `ms`, `verdict` contains one `Verdict`, `done` contains the review reference, and `error` contains a non-blank user-safe message. Unknown event types and unknown enum values are invalid at the API and browser boundaries.

`ProposalCreate` validation remains authoritative: title 1–300 characters, description 1–10,000 characters, canonical `city_id`, optional canonical `district_id`, non-empty sector, non-negative decimal budget, ISO dates with end not before start, optional canonical scenario key, and only `seeded` or `user` source. The proposal endpoint will assign the ID and `submitted_at` server-side. For the fixed cache flow, the server will reject a supplied noncanonical ID by not accepting client-generated IDs; it assigns `demo-proposal-01` only when the input has canonical `scenario_key`, `source=seeded`, and matches the cached proposal identity/content guard. All other proposals receive a UUID-derived canonical ID. This prevents a client from overwriting the demo or claiming seeded provenance.

`ClashReport` validation will require the report proposal ID to equal the review proposal ID, 1–5 verdicts in live mode, and exactly two candidates for the canonical cache file. The cache-specific validator will additionally require exactly one `OVERLAPPING`, one `COMPLEMENTARY`, `memo.recommendation == CO_FINANCE`, `source == seeded`, and a valid canonical coordination-focus district ID. All confidence values are finite and in `[0,1]`; each verdict cites a canonical project ID, non-empty reasoning, and attributes. These report-level rules sit in a dedicated cache/taxonomy service rather than over-constraining general live reports.

`SQLiteStore` will be extended with typed helpers required by the routes: review lookup/proposal lookup by review, pending/completed review status lookup, and audit listing as currently implemented. It remains the enforcement owner for durable state: `SUBMITTED → REVIEWED → APPROVED|REJECTED`, report/proposal atomic completion, and terminal approval transition. The API performs role validation before calling `record_approval`; the store will also reject a non-approver role defensively so an alternate caller cannot bypass the invariant. Every rejection attempt that reaches the API will receive an audit entry; successful decision writes remain atomic with state/status and approval. Database errors are recoverable API failures (500 with a safe message, full exception logged locally) and do not expose raw SQL or secrets.

## Data Pipeline, Providers, and Retrieval

`scripts/build_index.py` will continue to validate `data/processed/projects.csv` and optional `data/processed/seeded_projects.csv` separately using `Project`. It will collect invalid rows as `RejectedRow`, reject every duplicate project ID across the two accepted inputs, canonicalize exactly `name + description + themes`, and hash the full normalized project model for manifest comparison. Its Chroma metadata will retain project ID (as Chroma ID), city, district, sector, funder, approval/closing ISO dates, source, and content hash. It will stage and atomically replace only `data/index/index_manifest.json` after successful Chroma upserts/deletions; an embedding/Chroma error leaves the old manifest intact. The design accepts that Chroma’s internal writes cannot be transactionally rolled back, while the manifest remains the committed index view and the next incremental reconciliation repairs it.

`agent/retrieval.py` will change its public limit from the current 1–100 to 1–8. Its `SearchFilters` will add canonical sector and use canonical field names consistently (`city`, `district`, `sector`, plus inclusive implementation window). A candidate must match every supplied exact geographic/sector constraint and, when a complete date window is requested, have a complete project interval that intersects it inclusively. It will query sufficient Chroma records, normalize finite distances to `[0,1]`, deduplicate by ID using the best score, then sort by descending score and ascending project ID. Invalid filter keys, blank/noncanonical identifiers, invalid dates, reversed intervals, malformed Chroma output, absent index, and provider failures raise typed pipeline errors; routes map them to safe 400/503/502 responses according to the caller. Retrieval never runs for the canonical cached scenario.

`agent/embeddings.py` already uses `SentenceTransformer(..., local_files_only=True)` and will retain that offline behavior. It will ensure malformed vectors are rejected as `EmbeddingProviderError`. The Bedrock provider will create a fresh boto3 session after `PipelineConfig.from_environment(ROOT)` reloads `agent/.env` for each request; connect/read timeouts remain 20 seconds and retries remain disabled. `agent.errors.map_credential_error` maps `ExpiredTokenException`, `UnrecognizedClientException`, and `ExpiredToken` to `CredentialsExpired`, with the exact required message. No exception, audit summary, HTTP response, or diagnostics output may include credentials.

`scripts/check_aws.py` will load the refreshed config and independently invoke/check configured Nova Pro and Titan. It will print model IDs, callable/unavailable status, and token lifetime only when derivable without printing a token; it exits nonzero if either configured check fails. Expired credentials are a readable diagnostic rather than a traceback. `data/index/` and its manifest remain generated/git-ignored and rebuildable through `python scripts/build_index.py`.

## Deterministic Tools, Taxonomy, and Live Agent

The existing one-tool-per-file structure remains: `search_similar_projects.py`, `get_project.py`, `check_overlap.py`, `district_need.py`, and `draft_memo.py`. Each tool uses a Pydantic input/output model and a model-facing docstring. `check_overlap.py` is the deterministic evidence owner. It compares canonical city/district IDs, sector, explicit beneficiaries, concrete outputs, and inclusive dates extended exactly 12 calendar months on both ends. Missing location/date evidence is unknown/false rather than inferred. Its loading helper will search both processed and seeded project sources where appropriate, validating every returned record and preserving `source`/`source_url`.

A new `agent/taxonomy.py` will centralize post-processing for both cached and live verdicts. It receives a proposed `Verdict`, deterministic `OverlapFacts`, and proposal/project context, and returns a validated final verdict plus zero or more downgrade audit facts. It applies rules in this order:

1. A different city always downgrades `DUPLICATE`/`OVERLAPPING` to `COMPLEMENTARY` when sector/output relation is supported, otherwise `UNRELATED`.
2. Unknown districts never count as a match. Same city with different known districts cannot be `DUPLICATE`; `OVERLAPPING` needs explicit shared-beneficiary evidence and known time overlap.
3. Missing endpoint dates or lack of the exact 12-month-slack intersection prevents `DUPLICATE`/`OVERLAPPING` being justified by time; severity is lowered conservatively.
4. `DUPLICATE` requires same city, compatible district evidence, known overlapping period, at least two matching attributes, and explicit common concrete outputs. Otherwise it is downgraded to `OVERLAPPING` if supported, then `COMPLEMENTARY`/`UNRELATED` as facts permit.
5. Confidence is clamped to `[0,1]` and capped for incomplete facts; the model cannot raise severity beyond deterministic evidence. Every downgrade generates a short, redacted `taxonomy_downgrade` audit event.

`agent/prompts/clash_system.md` will contain the concise taxonomy, structured-output-only instruction, tool-use order, candidate cap, non-financial/human-signoff guardrail, and no-inference constraints; no prompt text will be embedded in Python. `agent/clash_agent.py` will load this file and construct exactly one Strands `Agent` per live review with the configured Nova Pro model ID. It will first retrieve at most eight filtered candidates, resolve deterministic packages, sort deterministically, and send at most five packages to the model. Each model call has a 20-second bound. Its output must parse as `ClashReport`; on Pydantic failure it retries once with the validation messages and then raises a readable `ReviewProviderError` for an HTTP 502. Tool/retrieval failure is a recoverable review failure, recorded in audit, which retains proposal `SUBMITTED`. Credential errors surface to the API as the exact 503 payload. Strands/Nova initialization is deferred until a non-cached review, so cached mode cannot instantiate it.

## Cached Demo Service

`data/demo_cache/demo-city-transit-01.json` will contain the proposal fingerprint/identity and the seeded `ClashReport`; a companion seeded project file, if required for verdict identity rendering, lives under `data/processed/seeded_projects.csv` and every row has `source=seeded`. The cache uses only canonical IDs and includes two valid project references, one overlapping and one complementary. It has `model_id` identifying cached demo execution and zero/known local latency; it does not imply that an AI call occurred.

A new `agent/demo_cache.py` will map the scenario key to a local path, read UTF-8 JSON, Pydantic-validate it, and apply the canonical composition checks above. It returns a fresh model copy per request and never imports retrieval, embeddings, boto3, or `clash_agent`. Missing file, malformed JSON, invalid schema, wrong proposal ID/scenario, unknown cached project/district, or wrong verdict composition produces `DemoCacheError` with a readable caller-safe message. It never mutates proposal or review state when parsing fails. These are recoverable 503 errors for a review request; the proposal remains `SUBMITTED`.

Cached review event choreography is generated deterministically in `agent/review_service.py`: `status` (“Loading seeded demo review”), local `tool_call` evidence events with fixed non-negative durations, the two report verdict events in cache order, then one `done` with `review_id`. The service persists the final validated report atomically through `SQLiteStore.complete_review` before emitting `done`; if completion fails it emits one `error` event and does not emit `done`. No events are generated after a terminal event. The live path uses the same generator and terminal handling, but its tool events come from its instrumented operations. A terminal event is replayable only by opening a completed review stream; the service may return its deterministic completed sequence or a clear conflict for unknown/non-pending reviews, but it must never run a second provider review.

## FastAPI API and Error Model

`agent/app.py` will become the composition root. It resolves `ROOT/data/atlas11.db`, creates/reuses one `SQLiteStore`, and exposes these contracts:

| Endpoint | Request | Success | Expected failures |
|---|---|---|---|
| `POST /proposals` | `ProposalCreate` | `201 Proposal` | `422` invalid payload; `409` stable demo/ID conflict; `500` safe store error |
| `POST /proposals/{proposal_id}/review` | no body | `201 ReviewCreated` | `404` unknown proposal; `409` not `SUBMITTED`/review exists; `503` invalid/unavailable cache or expired credentials; `502` live provider/tool/schema failure |
| `GET /reviews/{review_id}/events` | SSE | ordered `SseEvent` frames | `404` unknown review; stream carries one `error` terminal for an execution failure |
| `GET /reviews/{review_id}` | no body | `ClashReport` | `404` unknown; `409` incomplete/unvalidated review |
| `POST /approvals` | `ApprovalCreate` | `201 Approval` | `422` malformed/blank rejection reason; `403` role is not approver; `404` review missing; `409` incomplete/repeated/skipped decision; `500` safe store error |
| `GET /audit` | optional canonical `proposal_id`, `review_id` | `list[AuditEvent]` | `422` invalid filters; `500` safe store error |
| `GET /gaps` | optional canonical `district_id` | sorted list or one `DistrictNeedRecord` | existing `404` unknown district; existing `503` complete input unavailable |

The credential route mapping is deliberately an exception to FastAPI’s default `detail` shape: `CredentialsExpired` returns status 503 and exactly `{"error":"AWS credentials expired. Refresh agent/.env from Workshop Studio."}`. Other errors return `{"detail":"…"}` with safe human-readable text. The application logs exception context locally at warning/error level without request bodies that might contain secrets; the audit log stores only concise redacted factual summaries.

SSE will use `StreamingResponse(..., media_type="text/event-stream")`, serialize each Pydantic event with `event: <type>\ndata: <json>\n\n`, and include no credentials or raw provider response. The browser treats a received terminal event as final and closes/aborts the reader. The service ensures `status → tool_call* → verdict* → (done | error)` and exactly one terminal event; endpoint code must not append fallback events after the service finalizes. The report fetch follows `done`, not a verdict event, ensuring the browser displays only the persisted validated report.

`POST /approvals` does not call any funding/payment/allocation service because no such service will exist. It creates only an `Approval` record and displays `APPROVED`/`REJECTED` as a human coordination sign-off. A cached `redirect_district_id` updates returned/UI focus state only; `GET /gaps` remains a read-only view of the same generated data before and after approval.

## Frontend Architecture

`frontend/` will be created as a Vite React application with `src/main.tsx`, `src/App.tsx`, `src/index.css`, `tailwind.config.ts`, `postcss.config.cjs`, `tsconfig.json`, `vite.config.ts`, `package.json`, and strict `npm` scripts: `dev -- --host 127.0.0.1 --port 5173`, `build` (runs `tsc --noEmit && vite build`), `test`, and a typecheck alias. The Vite dev server will proxy `/api` to `http://127.0.0.1:8000`; `VITE_API_BASE_URL` optionally overrides it. The browser uses API paths after the configured base and never reads SQLite or files directly. Local static GeoJSON is copied/symlinked into `frontend/public/data/geo/` as a generated/reproducible asset copy from `data/geo/`, while gap values and snapshot/provenance come from `GET /gaps`; this avoids divergent generated data.

`frontend/src/types/contracts.ts` mirrors the backend’s public types as strict unions/interfaces: IDs are strings checked by a canonical-ID parser; source labels; `Role`, `ProposalStatus`, `VerdictLabel`, `Recommendation`; proposal/project/review/verdict/memo/report/approval/audit/gap/SSE types. `frontend/src/types/parse.ts` is a handwritten runtime validator with narrow `unknown` guards rather than a second schema library. It rejects extra-untrusted enum values, wrong scalar types, malformed IDs, nonfinite/out-of-range confidence/durations, and invalid event payloads before reducer updates. Parsing failures become readable `ApiError` values and never partially update application state.

`frontend/src/api/clashApi.ts` provides typed `createProposal`, `createReview`, `getReport`, `createApproval`, `getAudit`, and `getGaps`. A common fetch helper parses JSON safely, converts non-2xx responses into `ApiError { status, message, kind }`, and recognizes only the exact 503 `error` body as `credentialsExpired`. `frontend/src/api/reviewEvents.ts` implements a cancellable `fetch`/`ReadableStream` SSE parser using `AbortController`, emits validated events to a callback, and closes on the first `done`/`error` or abort. It does not use `EventSource`, which cannot set the application base path consistently and provides less explicit abort/error parsing control.

`frontend/src/hooks/useReviewWorkflow.ts` owns a `useReducer` state machine: `idle`, `submitting`, `creating-review`, `streaming`, `complete`, and `error`. State includes retained form values, proposal, review ID, pre-terminal trace events, report, error, selected role, selected candidate ID, focused district ID, drawer state, and persistent credential-warning state. Submitting validates client-side required fields, dates, and nonnegative budget; then it creates a proposal, creates one review, consumes one stream, and after `done` fetches the persisted report. It keeps form values and the last safe state on non-success responses. A cleanup effect aborts the stream on unmount/restart. Reducer guards ignore all events after its first terminal state, even if a malformed transport delivers them.

`frontend/src/components/ProposalForm.tsx` includes all `ProposalCreate` fields and a clearly labelled “Load seeded demo” action that fills the exact canonical scenario. It marks seeded input with `SeededBadge`; it does not let normal user input select `source=seeded`. `RoleToggle`, `ErrorBanner`, `CredentialExpiryBanner`, `SnapshotProvenance`, `StatusProgress`, and `SeededBadge` are small accessible shared components. The credential banner is non-blocking and remains until dismissed or a later successful non-expired request; cached review remains available.

`PlannerDashboard` uses the required control-room layout: a 360px, independently scrollable left proposal/verdict panel; a flexible center map workspace; and a closed-by-default right overlay drawer. Tailwind grid/flex sizing keeps the left panel at 360px and drawer trigger visible at 1366×768. The right drawer uses `role="dialog"`, an accessible label, Escape to close, focus moves into it on open and returns to the trigger on close, and focus is trapped while open. It must not change the left panel width.

`VerdictCard` renders all four labels as text plus closed palette color (`DUPLICATE #C0392B`, `OVERLAPPING #D68910`, `COMPLEMENTARY #138D75`, `UNRELATED #7F8C8D`), confidence with a labelled meter, matching-attribute tags, expandable reasoning, resolved project name/funder/amount, source/provenance badge, and “Show on map.” Projects are resolved from a typed API-provided candidate/project lookup carried in the report/service response or a minimal `GET /projects/{project_id}` endpoint if necessary; the design chooses a typed `project` object alongside each verdict in a new `ReviewCandidateDetail` API response to avoid unbounded browser CSV access and N+1 calls. The raw `ClashReport` stays unchanged for agent output; `GET /reviews/{id}` returns a `ReviewReportResponse { report, candidates: ReviewCandidateDetail[] }`, where each detail validates a `Project` record. This response is added to both Pydantic and frontend contracts.

`MapWorkspace` uses `react-leaflet` and OpenStreetMap tiles. It fetches `/data/geo/districts.geojson` and `GET /gaps`, joins only by canonical `district_id`, renders a sequential `need_score` choropleth, and includes a textual accessible legend showing each indicator-quality and snapshot/provenance. It displays “Map data unavailable; review and approval remain available” locally if either source is missing/malformed; no review state is disabled. Existing project markers, proposal marker, and proposal-to-candidate polylines render only when both endpoints have valid finite `[latitude, longitude]` coordinates. Because existing processed/cache project data lacks a guaranteed coordinate contract, absent coordinates yield no fabricated marker or line. The map shows candidate selection/highlighting when geometry exists. `GapCallout` and the memo drawer’s redirect action set `focusedDistrictId`, call Leaflet `fitBounds` for that district, and state: “Coordination focus only; this does not allocate or move funding.” The action never mutates fetched gap records.

`MemoPanel` renders recommendation, summary, redirect focus, and approval outcome. `AgentTrace` renders status/tool-call stages and durations. The drawer displays Approve/Reject only when `role === 'approver'`, the persisted proposal status is `REVIEWED`, and a final report/review ID exists. Planner users see an explanation of approver authority. Rejection requires a trimmed nonempty reason before API submission; API denial/error retains `REVIEWED` state and displays an error. No decision/redirect copy uses payment, allocation, commitment increase, or funded-district claims.

## Error Handling and Observability

Every operation has a defined caller result. Invalid client payloads are fatal to that request but recoverable to the user (`422` and inline form/API error). Missing proposal/review/project/district is recoverable (`404`). Invalid lifecycle position, duplicate review, or repeated decision is recoverable (`409`) with no state mutation. Planner authority is recoverable (`403`) with no state mutation. Cache/gap/index unavailable is recoverable (`503`); the map has a local fallback and the cached review preserves proposal safety. Live model output/tool failure is recoverable as review failure (`502` or stream `error`), logged and audited without a completed report; proposal remains `SUBMITTED`. Store/unexpected server errors are safe `500` failures, logged at API level, never shown with stack traces.

Cache parsing, taxonomy changes, review lifecycle creation/completion/failure, each tool call, each emitted verdict, approval/rejection attempt, and successful approval/rejection append redacted UTC audit rows. Audit payload summaries include factual IDs and outcomes but omit credentials, raw headers, and model dumps. Logging records exception class/context and identifiers, never AWS keys/tokens, authorization, or free-text secrets. `GET /audit` returns parsed audit models sorted by timestamp/event ID and filters by supplied canonical IDs.

## Validation Strategy

Python unit tests will cover Pydantic validators; CSV duplicate/provenance/date rules; cached local embedding no-download behavior; Titan/Nova timeout and credential mapping; index reconciliation and manifest preservation; retrieval ordering/unique/score/filter boundaries; all deterministic tools; taxonomy city/district/date/concrete-output downgrades; cache composition and no-AWS/no-Chroma mocks; store approval/audit atomicity; FastAPI route/status/error payloads; SSE ordering and terminal exclusivity; and gap read-only semantics. Hypothesis tests will prove overlap symmetry, cross-city severity exclusion, duplicate evidence minimum, verdict confidence/label closure, approval state-machine reachability, SSE terminal invariants, retrieval ordering/filter bounds, gap numeric invariants, and redirect immutability.

Frontend Vitest tests will exercise parsers, exact REST serialization, typed errors/credential banner, SSE abort/terminal cleanup, reducer sequencing and post-terminal ignores, form retention, source/snapshot display, role gating, all verdict labels, drawer keyboard focus, memo rejection validation, map unavailable behavior, no-link-on-missing-coordinates, and redirect focus without data mutation. fast-check properties will generate accepted event sequences, valid verdicts, role/status combinations, seeded sources, redirect data, and missing coordinate permutations. A mocked canonical UI integration test asserts exactly one `OVERLAPPING`, one `COMPLEMENTARY`, `CO_FINANCE`, seeded badge, approver action, and non-financial focus wording.

The integration gate is `scripts/demo_smoke.py` run with `DEMO_MODE=cached`: it creates the canonical seeded proposal, creates a review, consumes/validates ordered SSE, fetches the persisted report, approves as an approver, reads audit and gaps, and asserts exact IDs/composition/provenance plus unchanged gap need/commitment/funding fields before and after focus. It mocks or fails AWS/Bedrock/retrieval construction to prove the cache path does not use them. The frontend smoke is run at 1366×768 when browser tooling is available; otherwise component/layout tests and the documented limitation are the evidence.

Validation runs only after each corresponding task is implemented and before its checkbox is changed: activate `.venv`, run narrow `pytest`/Hypothesis selectors and `ruff check`/`ruff format --check` for changed Python; run narrow Vitest/fast-check selectors, `npm run typecheck`, and `npm run build` for frontend. Port 8000 is checked and the externally managed API is reused; no second API process is started. The frontend runs at port 5173 only after checking it is free.

## Out of Scope and Deferrals

This design deliberately excludes payments, allocations, commitments, procurement, actual funding redirection, authentication/production authorization, hosted vector stores, live scraping during the demo, direct raw-data edits, unpinned packages, and claims of real-world impact or accuracy not computed from sourced data. Bedrock account/model availability is not guaranteed; the exact cached mode is the required fallback. Existing illustrative demo districts retain their `indicator_quality=illustrative`, `source=seeded`, and `snapshot_date=TBD: needs source`; UI and presentation copy must not elevate them to measured city evidence. Map tiles are optional network access and failure leaves the application functional. No commit, push, history change, or extra API instance is part of implementation.
